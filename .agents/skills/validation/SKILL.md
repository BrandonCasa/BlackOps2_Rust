# Validation

## Bounded task

Validate one task/diff against its assignment, handoff and completion criteria.
Specify revision/working-tree scope, applicable gates and expected artifacts.
Read [project rules](../../../AGENTS.md),
[architecture](../../../docs/architecture/README.md), project state and previous
handoff. Do not spawn agents, commit or expand a review into new feature work.

## Investigation

1. Inspect Git status/diff and all candidate additions, including untracked files.
   Account for existing edits; do not revert work outside the reviewed task.
2. Trace implementation claims to original evidence and meaningful test cases.
   Inspect dependency direction, abstraction reuse, Bevy facility use, safe Rust
   policy, fixed-step ordering and replay assumptions where the change touches them.
3. Check candidates for proprietary assets/scripts/dumps, secrets, real installation
   paths and generated builds. Verify ignore behavior and placeholder configuration;
   ignores alone do not establish that a candidate is acceptable.
4. Verify tool availability and selected stable Rust/Bevy compatibility before
   interpreting build results. Record unavailable tools instead of provisioning
   them unless provisioning itself is the separately assigned objective.
5. Separate code correctness, structural review, executable/runtime checks,
   original-game comparisons and profiling evidence in the acceptance record.

## Required evidence

Record reviewed files/revision, evidence/test links, exact commands, exit results,
relevant failures, skipped/unavailable gates and unresolved claims. Update only
assigned project-state/handoff records; use `docs/fidelity/` for existing comparison
results. Keep raw proprietary output and machine-specific paths external.

## Implementation expectations

Validation may run checks and make assigned documentation corrections. Report
code defects for a bounded repair; change code only if repair is explicitly in
scope. Do not weaken lint/tests, unsafe policy, tolerances or architecture gates
to obtain green results. Retain `Cargo.lock` once legitimately generated by Cargo.

## Validation procedure

For workspace code integration, run the baseline when tooling is available:

- `cargo metadata --no-deps --format-version 1`
- `cargo test --workspace`
- `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets -- -D warnings`

Use focused checks during iteration and change-specific parser/link/skill checks
for documentation-only tasks. Include meaningful error-path/replay tests when
applicable. Record what ran; successful compilation is not gameplay fidelity.

## Handoff and escalation

Save and return the [required handoff](../../../AGENTS.md#required-handoff).
Determine `COMPLETE`/`PARTIAL`/`BLOCKED` from actual acceptance criteria and report
unverified gates. Preserve scoped fidelity evidence; never promote to
`MATCHED`/`VERIFIED` from tests alone. Report missing tooling, contaminated
candidates, conflicting evidence or material out-of-scope repairs to the outer
agent without introducing a new approval gate or claiming unavailable checks passed.
