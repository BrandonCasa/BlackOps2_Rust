## Findings

### P2 - Resolve the cinematic sound reference to an audio alias

- **Code:** `src/cinematics.rs:44`; `src/origins/content.rs:785-790,1454-1462`; `src/audio.rs:397-400`.
- **Trigger:** Package an intro/loading sequence with a valid `audio` reference to a content sound, whose content ID differs from its alias.
- **Draft behavior:** Content validation requires `CinematicSequence.audio` to identify a `sound`, but `loading_start` passes that ID directly to `audio::emit`. The mixer looks up the string in `game.audio.aliases` and rejects an unknown alias. A valid packaged cinematic can therefore play silently.
- **Evidence and impact:** This contradicts the existing sound-reference contract. The ending path has the same ID-versus-alias defect recorded in `7df83438a3215c3864370b84830c26873b4753ac.md`; this commit independently introduces it into loading playback. The earlier audio state restriction is already relaxed by `3b2e967b38dd0d6bbbb34fb964653e2618055e5e`, which permits PreparingShaders, so state rejection is not the issue here.
- **Future correction:** Resolve the sound definition and emit its alias, preserving the selected sequence's audio identity. Cover both cinematic callers when implementing the earlier finding.

### P2 - Wait for frame readiness before consuming its playback interval

- **Code:** `src/cinematics.rs:43,46,50-53`.
- **Trigger:** Start a packaged sequence on a cold asset cache or with frame loading slower than its display interval.
- **Draft behavior:** Playback starts counting elapsed time immediately. Only the first image is requested at startup; each later image is requested when its interval has already begun. No loading state is checked before the timer advances or the sequence completes. Time spent loading is consumed as if frames had been displayed, and frames whose entire interval passes during loading are never presented.
- **Evidence and impact:** Bevy's pinned AssetServer returns handles while loading proceeds asynchronously; receiving a handle is not evidence of image readiness. The resulting blank/skipped opening frames and shortened visible sequence are code-level integration risks, not a claim of observed rendering or an inferred native movie timing. This also prevents a dependable correspondence between frame timing and audio.
- **Future correction:** Prepare the required frame assets or a bounded ready buffer before starting the playback clock, handle load failures, and advance presentation according to the chosen media timing policy. Preserve skip responsiveness during loading.

### P2 - Do not charge completed shader preparation for time spent playing the intro

- **Code:** `src/rendering/preparation.rs:97-106,158-168,179-199`; new gate at `:190`.
- **Trigger:** A valid, unskipped loading sequence lasts beyond the shared 180-second preparation deadline, even though shaders, surfaces, and rigs have settled.
- **Draft behavior:** This commit keeps the application in PreparingShaders until `loading.done`, but the unconditional shader timeout remains active from state entry. The timeout sends the application to LoadError after 180 seconds while all shader work may already be complete. Cinematic validation requires positive FPS and nonempty frames but imposes no shorter duration bound.
- **Impact:** Valid playback can fail startup with an inaccurate shader-preparation timeout. It also couples media duration to a deadline intended for shader readiness, contrary to the commit's separate-gate intent.
- **Future correction:** Track shader completion/deadlines independently of cinematic completion and allow the two readiness gates to finish independently. Do not silently impose a movie length limit by retaining a completed shader timeout.
