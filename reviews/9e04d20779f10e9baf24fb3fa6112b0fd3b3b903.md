## Findings

### P2 — Quick Revive is excluded before the special solo eligibility check

**Draft:** `src/perks/vendors.rs:51–62`, especially line 55; `src/origins/content.rs:447–456`; the `perk.quick_revive` entry in `assets/origins/game.json`.

**Reference:** `todo-audit-20261010/decompiled/t6/zm_tomb.gsc:1191–1202` (`include_perks_in_random_rotation`) explicitly includes `specialty_quickrevive`; `todo-audit-20261010/decompiled/t6/zombies/_zm_perk_random.gsc:494–516` skips already owned perks when selecting a result.

With an available solo Quick Revive purchase and an unowned Quick Revive, `roll` first skips every definition for which `has_supported_effect()` is false. Quick Revive intentionally has none of that helper's general-purpose effect fields because its behavior is implemented by the solo revive system. It therefore never reaches the following `can_buy_solo` check and can never appear in Wunderfizz. The existing drink completion path in `src/perks.rs:159–166` already supports this special perk. Admit the solo-revive definition through the supported-effect filter, then apply its purchase eligibility rules.

### P2 — The rare-perk gates remove candidates instead of reproducing the source's weighted ordering

**Draft:** `src/perks/vendors.rs:51–62`.

**Reference:** `todo-audit-20261010/decompiled/t6/zm_tomb.gsc:424–447` (`tomb_random_perk_weights`), together with the complete rotation at `:1191–1202`; `todo-audit-20261010/decompiled/t6/zombies/_zm_perk_random.gsc:494–516` (`get_weighted_random_perk`).

The draft gives each of five perks a 25% chance to enter a temporary eligible pool and then chooses uniformly from that pool. Whenever at least one ordinary perk remains eligible, a rare perk whose gate fails has zero chance on that roll. The source starts with the full registered rotation, randomizes that rotation and the gated list, combines them to produce the order, and takes the first unowned result. It does not implement the draft's filter-and-uniform-choice algorithm. For example, when all five gates fail, the draft's ordinary-perk pool excludes all five gated perks, whereas the source still feeds its registered rotation into the ordering operation. This changes the resulting perk distribution as the player acquires perks. Reproduce the source array-combination and first-unowned selection semantics rather than using candidate exclusion. The precise numeric distribution is not asserted here because the engine's `arraycombine` implementation is not present in the recovered script set.

### P2 — Active-machine, roll, bottle and relocation state have no world presentation

**Draft:** `src/perks/vendors.rs:40–44`, `:64–92`, `:125–127`, `:130–141`.

**Reference:** `todo-audit-20261010/decompiled/t6/zombies/_zm_perk_random.gsc:191–229` (bottle model setup and active `j_ball`), `:252–274` (power/active lights), `:288–299` (active location indicator and animation), `:344–373` (cycling and result/bear models), `:519–533` (bottle motion), and `:640–655` (start/loop/stop/leave sound sequence). The original machine model is identified in `game-prepare/entities/maps/mp/zm_tomb.d3dbsp.ents:27437–27519`.

The six new `Machine` entities contain only marker, transform and visibility components. Neither setup nor phase transitions attach or address a scene, bottle, ball, location indicator, light, or machine animation. The only world sound emitted is a bear alias after the full seven-second bear interval. A player therefore receives proximity prompts but gets none of the original world cues identifying the active powered machine, showing the four-second cycling result and available bottle, displaying the bear after the four-second cycle, or showing the machine move. Any existing imported static machine geometry does not gain these state changes merely from the marker entities. Connect the recovered machine/bottle presentation and source sound sequence to the transaction phases, including a separate three-second visible bear phase before refund/relocation.

### P3 — Reloading unnecessarily blocks both buying and taking the bottle

**Draft:** `src/perks/vendors.rs:115–120`, `:130–135`.

**Reference:** `todo-audit-20261010/decompiled/t6/zombies/_zm_perk_random.gsc:153–169` (`can_buy_perk`) excludes drinking, mine/blocking equipment, revive interaction and no weapon; `:399–441` (`grab_check`) starts the bottle switch for an eligible owner rather than requiring the weapon's reload action to be idle.

The shared `busy` flag rejects every `WeaponAction` other than `Ready`. A player who is reloading when pressing use cannot buy a roll or take an available bottle, even with a normal held gun and no prohibited activity. The source eligibility allows that situation and begins the bottle weapon change. This is especially visible when the ten-second bottle timeout is nearly over. Match the source's blocking activities and safely cancel/transition the reload through the normal bottle-switch path rather than making `Ready` a universal prerequisite.
