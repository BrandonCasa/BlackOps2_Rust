## Findings

### P2 - Clear or hide the new inventory and perk roots when leaving gameplay

- **Code:** `src/hud/origins.rs:9-15,24-26,33-36`; integration in `src/frontend.rs:195-205`, `src/session.rs:86-94`, and `src/hud.rs:270-284`.
- **Trigger:** Acquire a perk or equipment, then quit to the main menu; also pause or enter Game Over while the scoreboard inventory or generator-attack text is visible.
- **Draft behavior:** Both roots are created once at Startup, are not `SessionEntity`, and have no non-playing cleanup or visibility system. `update` and `icons` stop running outside Playing. Teardown removes the player and session entities but leaves these roots and the last perk children intact. The main menu covers only its central panel, so old inventory/perk information remains at the left edge; scoreboard and attack text can remain frozen after their input/state ceased to apply. Existing `HudText` explicitly clears or replaces its content for these states, but that handling does not cover the new roots.
- **Reference:** `todo-audit-20261010/decompiled/t6/zm_tomb_craftables.gsc:595-602,1333-1368` explicitly updates and clears player-specific inventory clientfields as ownership changes. Native field state is tied to the live player/game state, rather than retaining a previous session's inventory. This is a lifecycle integration defect independently of the intentionally approximate text layout; exact native menu layout was not accepted or inferred from these scripts.
- **Impact:** False carried equipment and stale attack/progression information survive a completed or abandoned session and contaminate frontend/pause presentation.
- **Future correction:** Give both roots an explicit gameplay/session visibility and cleanup path, and refresh their cached children when the player/session changes. Ensure releasing Scoreboard outside Playing cannot leave its expanded content on screen.

### P2 - Distinguish uncrafted staffs from crafted base staffs in the new scoreboard

- **Code:** `src/hud/origins.rs:19-20,29`; integration in `src/crafting.rs:17-20,133-147` and `src/staff_upgrades.rs:9-15`.
- **Trigger:** Open the scoreboard immediately after starting a session, after finding only a record/crystal, or after crafting just one element.
- **Draft behavior:** Every element is printed as `base` whenever its upgrade flags are false. The row never consults `crafting.crafted`, part/crystal state, or actual staff ownership. It therefore announces four base staffs in a fresh game and presents an unbuilt element identically to an assembled staff ready for use.
- **Reference:** `todo-audit-20261010/decompiled/t6/zm_tomb_craftables.gsc:333-376` registers separate piece, player ownership, and element quest-state fields; `:682-707` advances the relevant element to crystal-found state 2; `:776-797` sets state 3 only when that staff is fully crafted; `:1333-1368` separately sets/clears carried staff ownership. These are behavioral state distinctions, not a requirement to copy an undocumented HUD layout.
- **Impact:** The inventory readout cannot tell the player which staffs actually exist or which element still needs assembly, despite presenting a definitive base/upgraded status.
- **Future correction:** Derive each row from the element's assembly/availability state before displaying base/upgraded, and distinguish ownership or placement where the chosen readout purports to describe inventory. Preserve the original element mapping explicitly.

### P2 - Do not display a destroyed shield from the stale selected-equipment string

- **Code:** `src/hud/origins.rs:21,27`; integration in `src/buildables.rs:98-100` and `src/damage.rs:248-250`.
- **Trigger:** Exhaust a carried shield through melee wear or incoming blocked damage while `equipped` remains `tomb_shield_zm`.
- **Draft behavior:** Both existing destruction paths remove the shield from `owned` and set `shield_held` false but leave `equipped` intact. The newly added HUD unconditionally prints that string. It continues to advertise a shield even though health is zero, ownership is absent, and the shield activation branch rejects it. This report concerns the new readout's use of stale state, not a re-review of the inherited shield damage model.
- **Reference:** `todo-audit-20261010/decompiled/t6/zombies/_zm_weap_riotshield_tomb.gsc:267-295` routes exhausted shield health through removal; `:161-202` removes both the weapon/equipment and the carried/equipped flags. Source equipment state ceases to identify a usable carried shield once destroyed.
- **Impact:** The player receives an incorrect equipment-available cue and no indication from this new readout that replacement is needed.
- **Future correction:** Display carried equipment from validated ownership and usable state, and normalize the selected-equipment value on destruction. Keep selection distinct from possession if stale selection is intentionally retained for input routing.
