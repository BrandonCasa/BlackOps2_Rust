### P1 — Shield bashes use the unused 75-point constant instead of the source fling damage

- Draft: `src/buildables.rs:90-97`.
- Reference: `todo-audit-20261010/decompiled/t6/zombies/_zm_weap_riotshield_tomb.gsc:21-29`, `:388-414` (`riotshield_fling_zombie`), `:454-531` (`riotshield_get_enemies_in_range`), and `:548-586` (`riotshield_melee`).
- Trigger: bash a live ordinary zombie within the 90-source-unit fling range.
- Current behavior: applies 75 melee damage and 0.8 seconds of stun to every selected target, at a yaw-only dot threshold of 0.4.
- Reference behavior: the configured fling range is 90 units (2.286 m); targets inside it use `riotshield_fling_zombie`, which applies 2500 impact damage and flings a killed ragdoll. The `riotshield_gib_damage = 75` constant is not the damage applied by that function. The reference uses the weapon-forward vector, a forward-hemisphere test, centroid/eye range, and cone visibility.
- Impact: an early-round zombie that should die to the shield instead survives repeated hits, consuming the shield's limited bash durability. Target acceptance also changes when looking up/down or hitting near the edge.
- Correction direction: reproduce the source target classification and fling/knockdown outcomes rather than using the nearby constant as a universal damage value. Retain the source shield wear per affected target.
- Tip status: still present in the reviewed tip.

### P2 — Raising the shield leaves firearm actions and presentation active

- Draft: `src/buildables.rs:55-67`, `:82-89`.
- Reference: `todo-audit-20261010/decompiled/t6/zombies/_zm_riotshield_tomb.gsc:195-242` (`trackriotshield`); `todo-audit-20261010/decompiled/t6/zombies/_zm_weap_riotshield_tomb.gsc:364-372` only bashes when the actual shield weapon emits melee.
- Trigger: raise the shield during a burst, reload, pending knife action, or weapon transition; alternatively press reload or weapon-cycle with the shield raised.
- Current behavior: toggles a boolean and suppresses only fire/melee/ADS input bits. It never cancels the gun's existing `WeaponAction`, suppresses reload/cycle/slot input, or selects the shield presentation. `src/weapons.rs:990-1007` continues a previously queued burst even without fire input, so bullets can still be emitted behind an active blocking shield. The old gun remains the inventory/presentation weapon.
- Reference behavior: raising the shield is a weapon switch, with shield-specific equip, viewmodel, move scale, and action timing. The previous firearm action is interrupted by the switch.
- Impact: combined firearm/shield behavior and first-person feedback differ materially from the original; the player can retain front protection through actions that belong to the stowed gun.
- Correction direction: integrate a temporary equipment weapon/action state with the existing weapon path, cancel incompatible pending emissions, and restore the prior gun only when the shield is stowed.
- Tip status: still present.

### P2 — Taking and launching the drone makes an owned shield inaccessible

- Draft: `src/buildables.rs:55-79`; collection integration at `src/crafting.rs:144-150`.
- Reference: `mechanics-quests-01/decompile/decompiled/t6/_zm_equipment.gsc:803-810` assigns equipment to action slot 1; `todo-audit-20261010/decompiled/t6/zm_tomb_craftables.gsc:1068-1075` assigns the drone to its separate action slot (default slot 2).
- Trigger: own a shield, take the Maxis Drone, and deploy the drone.
- Current behavior: taking the drone overwrites the only `equipped` string; deployment clears that string. The shield remains in `owned` with health, but the only buildable action matches `equipped`, so it can no longer be raised. Taking another shield at the bench is rejected as a duplicate.
- Reference behavior: the shield and drone have independent activation paths and can coexist.
- Impact: acquiring a second buildable disables normal use of the first until its health is exhausted through rear hits.
- Correction direction: keep independent ownership/activation state for shield and drone, or provide a selection path that can reach every owned item and restore it after deployment.
- Tip status: still present.

### P2 — A player can create unlimited persistent deployed shields by returning to the bench

- Draft: `src/buildables.rs:60-66`; replacement check at `src/crafting.rs:145-150`.
- Reference: `todo-audit-20261010/decompiled/t6/zombies/_zm_riotshield_tomb.gsc:221-240` destroys an existing deployed instance when the shield is acquired again; `todo-audit-20261010/decompiled/t6/zombies/_zm_weap_riotshield_tomb.gsc:161-200` manages the owned/deployed shield lifecycle.
- Trigger: deploy a shield, take a replacement from its workbench, and repeat.
- Current behavior: the deployed entity has no owner component/reference. Deployment removes the shield from `owned`, so the bench grants another one; none of the prior deployed entities is removed. Every surviving copy attracts ordinary zombies.
- Reference behavior: a player's shield tracks one deployed instance and replaces/destroys it when a fresh shield is acquired.
- Impact: a free bench becomes an unlimited source of persistent colliders and zombie decoys.
- Correction direction: track deployed shield identity per owner and retire the previous instance when collecting/replacing the shield, using the source ownership lifecycle.
- Tip status: still present.

### P1 — Maxis Drone abandons a downed player instead of performing its revive task

- Draft: `src/buildables.rs:122-125`, `:132-136`.
- Reference: `todo-audit-20261010/decompiled/t6/zombies/_zm_ai_quadrotor.gsc:407-448`, `:1189-1200` select a last-stand player within 500 units and issue `remote_revive`; `todo-audit-20261010/decompiled/t6/zm_tomb_craftables.gsc:848-856` requests return on bleedout/disconnect, not on entering last stand.
- Trigger: a player becomes downed while the deployed drone is nearby and its active timer has not expired.
- Current behavior: any owner state other than `Standing` permanently sets `returning`; the function then skips all combat and contains no revive target/path/notification logic.
- Reference behavior: prioritizes the nearby downed player, approaches the revive location, waits for the revive effect, and revives through the normal remote-revive path. Owner bleedout/disconnect is a different return condition.
- Impact: a central Maxis Drone survival ability is absent, and the owner downing causes the opposite behavior.
- Correction direction: add a revive substate through the normal life-command/message path, with readiness/range/path checks and cancellation on recovery, bleedout, disconnect, or actual expiry. Do not use `not Standing` as the return condition.
- Tip status: still present.

### P2 — Drone firing has no source burst and pause cadence

- Draft: `src/buildables.rs:138-150`.
- Reference: `todo-audit-20261010/decompiled/t6/zombies/_zm_ai_quadrotor.gsc:140-163`, `:855-880` fires for a random 1.5–3 seconds and pauses 0.5–1 second when the enemy is AI.
- Trigger: a visible zombie target stays in the valid 96–384-unit band, or new valid targets continue appearing.
- Current behavior: immediately fires every weapon interval for the whole outing whenever any target is available. There is no firing-window or inter-burst pause state.
- Reference behavior: uses weapon fire intervals inside bounded bursts, then yields before beginning the next attack.
- Impact: sustained damage and target turnover are consistently higher than the source drone even when the turret weapon data matches.
- Correction direction: retain the weapon interval inside a source-matched burst/pause state machine and handle target loss/return transitions at those boundaries.
- Tip status: still present.

## Remaining boundaries

The source active lifetime of 80 plus 10 seconds and 60-second recharge are represented. Return flight is explicitly approximate; the current fallback timeout also counts from active lifetime rather than from entering return, so an early return needs its own bounded timeout when that path is implemented. Exact crash visuals, drone quest pickups/upgrades, shield damage models, and multiplayer ownership need further integration review. No runtime success is claimed.
