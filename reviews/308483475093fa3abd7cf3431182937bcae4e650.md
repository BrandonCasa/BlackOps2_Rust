## Findings

### P1 — A 2000-point attachment reroll also supplies a full ammunition refill

- **Original code:** `src/stations.rs:226-244,249-254`; `src/weapons.rs:339-356,409-428`.
- **Reference:** `damage-life-state-03/decompiled/t6/_zm_perks.gsc:577-592,709-715,765-777`.
- **Trigger:** Deposit an eligible upgraded gun after spending ammunition, then collect its attachment reroll.
- **Reference behavior and impact:** The original distinguishes an attachment purchase from the first upgrade. It records the old magazine, magazine capacity, reserve, and maximum ammunition, then restores the old amounts with adjustments only for capacity changes. Here `deposit_active()` returns an `OwnedWeapon`, but the transaction discards that value; the processing state retains only the weapon ID. Collection unconditionally calls `fill_received()`, setting both magazine and reserve to their maxima. An empty upgraded HAMR, for example, can buy all 125 magazine rounds and 625 reserve rounds for 2000 points while also rerolling. This changes ammunition scarcity and the value of Max Ammo and wall ammunition.
- **Future correction:** Preserve the deposited weapon's ammunition and relevant capacity information in the pending transaction. Restore it for repeat purchases according to the source capacity-delta rule, and retain full starting ammunition for a first upgrade.

### P2 — The first upgrade randomly chooses an attachment instead of applying the source default

- **Original code:** `src/stations.rs:69-90,232-235,254`.
- **Reference:** `mechanics-economy-02/decompiled/t6/_zm_weapons.gsc:578-597,1757-1777`; `damage-life-state-03/decompiled/t6/_zm_perks.gsc:583-585,631`; `weapon-materials-20261010/native-camos/options-patch_zm/zm/pap_attach.csv:1-3,6-18,25-29`.
- **Trigger:** Pack-a-Punch an unupgraded weapon with a table entry, including a first HAMR, Type 25, DSR, or Chicom upgrade.
- **Reference behavior and impact:** The source reads column 1 as a separate `default_attachment`. `get_upgrade_weapon()` uses that default on the first upgrade; the random addon path is selected only for an attachment purchase. This implementation randomly samples the complete hardcoded list on both first and repeat purchases. A first Type 25 upgrade can therefore acquire `gl` or `mms` instead of the table's `reflex`, and a first HAMR can acquire `grip` instead of `none`. The player receives an unpredictable first-upgrade configuration and early access to outcomes reserved for repeat purchases.
- **Future correction:** Represent the default separately and apply it deterministically on the first upgrade. Normalize the source `none` value explicitly instead of treating the invented `defaultattachment` sentinel as an actual table entry.

### P2 — Reroll eligibility and outcomes include the default column as an extra addon

- **Original code:** `src/stations.rs:69-90,227,234-235`.
- **Reference:** `mechanics-economy-02/decompiled/t6/_zm_weapons.gsc:589-597,1605-1643,1782-1813`; `weapon-materials-20261010/native-camos/options-patch_zm/zm/pap_attach.csv:1-3,9,15,17-18,24-29`.
- **Trigger:** Attempt to reroll an upgraded AK-74u, FAL, Galil, or KSG; or repeatedly reroll one of the genuinely eligible upgraded guns.
- **Reference behavior and impact:** The original enables repeat purchases only when the addon list has more than one entry, and samples that list while excluding the current addon. The default is not automatically part of the addon list. AK-74u, FAL, Galil, and KSG rows have a fixed reflex default and zero addons, but the draft invents a two-entry `[defaultattachment, reflex]` list and permits 2000-point rerolls on all of them. For eligible guns, it also adds an unsupported return to `defaultattachment`; Type 25 and SCAR can return to their default reflex despite reflex not appearing in their addon columns. These alter both which guns accept repeat purchases and the probabilities and reachable results of every reroll.
- **Future correction:** Preserve the table's separate default and addon columns, derive eligibility from the addon count, and sample only the applicable addon entries while excluding the actual current attachment. A default may be rolled only when it is also explicitly present in the addon columns, as with DSR `vzoom` and Chicom `reflex`.

### P1 — Select Fire and grenade-launcher rolls cannot activate their native alternate weapons

- **Original code:** `src/stations.rs:86,89,254`; `src/weapons.rs:319-329,375-381,1074-1102`; integration at `src/gameplay.rs:165,262-265,314-318`.
- **Reference:** `solo-content/source/attachmentunique/au_qcw05_upgraded_sf:1` (`altWeapon=sf_qcw05_upgraded_zm` and select-fire transition animations); `solo-content/source/weapons/qcw05_upgraded_zm:1` (`fireType=4-Round Burst`); `solo-content/source/weapons/sf_qcw05_upgraded_zm:1` (`fireType=Full Auto`, shared ammunition identity, return alternate); `solo-content/source/attachmentunique/au_type95_gl:1` (`altWeapon=gl_type95_zm`); `solo-content/source/weapons/gl_type95_zm:1` (one-round projectile launcher and return alternate).
- **Trigger:** Collect Chicom `sf` or Type 25 `gl`, then attempt to use the alternate firing mode.
- **Reference behavior and impact:** The source attachments install real alternate weapon definitions, with their own fire mode, ammunition behavior, transitions, and projectile delivery. Here collection only changes a string. `sf` merely applies a 0.85 spread multiplier, leaving the Chicom's four-shot burst definition active. `gl` has no consumer beyond attachment selection and storage. The only alternate-mode input path operates on upgraded staffs. Consequently neither paid outcome supplies its defining function: the Chicom cannot switch to automatic fire, and the Type 25 cannot launch a grenade.
- **Future correction:** Add reusable attachment alternate-mode handling through ordinary input, retaining source transitions and the correct ammunition relationship. Resolve firing and projectile delivery from the selected alternate definition. Do not approximate Select Fire by reducing spread.

### P2 — Scope and sight rerolls leave aiming behavior unchanged

- **Original code:** `src/stations.rs:74,77-89,254`; `src/weapons.rs:233-241,319-329`; ADS processing at `src/weapons.rs:808-823`.
- **Reference:** `solo-content/source/attachment/is:1` (`adsZoomFov1/2/3=50`, `adsTransInTimeScale=0.85`); `solo-content/source/attachment/acog:1` (`adsZoomFov1/2/3=35`); `solo-content/source/attachment/vzoom:1` (additional FOV values 15 and 35 and different zoom fractions); `solo-content/source/attachmentunique/au_dsr50_vzoom:1` (`scope_overlay_vzoom` and scope model); `solo-content/source/attachmentunique/au_dsr50_is:1-4` (sight hiding and no scoped overlay).
- **Trigger:** Reroll a DSR or Ballista between available iron-sight and scoped configurations, or receive one of the other optical attachments.
- **Reference behavior and impact:** The native assets change the effective sight, magnification, and in some cases ADS transition timing. The newly stored attachment is not read by `ads_fov()`, ADS timing, or sight selection. `is`, `acog`, `vzoom`, `reflex`, `rangefinder`, and `mms` all fall through the new modifier accessors. In particular a DSR iron-sight roll retains the same aiming parameters as its scoped state, and variable zoom has no input or magnification state. The paid result does not change the player's ability to aim as its native counterpart does.
- **Future correction:** Resolve effective ADS parameters, sight presentation, and supported optical controls from the attachment and weapon-specific override definitions. Use the original assets for sight models and overlays when integrating presentation.

### P2 — The new modifier values contradict the recovered attachment definitions

- **Original code:** `src/weapons.rs:325-329,568-571,785`; application at `src/gameplay.rs:279-290,353-357`.
- **Reference:** `solo-content/source/attachment/grip:1` (`hipSpreadMinScale=1`, `hipSpreadMaxScale=1`, `adsViewKickCenterSpeedScale=1.02`); `solo-content/source/attachment/dualclip:1` (reload and empty-reload scales 0.675); `solo-content/source/attachment/extbarrel:1` (`damageRangeScale=1.16`); `solo-content/source/attachment/sf:1` (spread scales 1 and alternate-mode behavior); weapon-specific examples in `solo-content/source/attachmentunique/au_hamr_grip:1` and `au_qcw05_upgraded_dualclip:1`.
- **Trigger:** Fire or reload a gun after collecting `grip`, `dualclip`, `extbarrel`, or `sf`.
- **Reference behavior and impact:** The draft grants grip a 20% spread reduction, including interpolated ADS spread, and a 25% reduction to recoil impulse. The recovered generic grip asset instead leaves spread unchanged and adjusts ADS centering speed by 1.02; its weapon-specific assets supply pose/animation overrides rather than these invented bonuses. Dualclip advances the reload clock by 1.25, producing a duration factor of 0.8 rather than the recovered 0.675. For the Chicom's 2.1-second reload, those are 1.68 seconds versus 1.4175 seconds before other modifiers. Extended Barrel uses 1.2 rather than 1.16, shifting damage falloff and kills at range. The `sf` spread bonus is likewise absent from its generic attachment asset. These are measurable weapon-balance differences, not missing numerical evidence.
- **Future correction:** Import and compose the original attachment fields and applicable unique overrides. Map recoil recovery separately from kick impulse, preserve hip and ADS distinctions, and apply native reload and damage-range scales. The draft's suppressor scale also differs from the generic recovered 0.7, but the currently eligible DSR has equal maximum/minimum damage, so that range discrepancy alone is not asserted here as a current damage regression.

### P1 — The penetration exit calculation cannot traverse the map's open collision patches

- **Original code:** `src/hit_regions.rs:161-179`; collider construction at `src/assets.rs:488-506`.
- **Reference:** Native ballistic capability is present in `solo-content/source/weapons/type95_upgraded_zm:3` (`penetrateType=medium`) and `solo-content/source/weapons/hamr_upgraded_zm:1` (`penetrateType=large`). The original commit's prepared `assets/origins/map.gltf` has LFS identity `sha256:7640d35e12e4a6a0f97441d5a4bacc71f9e42d2241f4c783e47ef644f9ad056b`; a matching local asset was read statically. Scene 1 mesh 88, `world_18_(np.int64(1), np.int64(-1), np.int64(-4))`, has two triangles and six vertices all at X=20.11680030822754. It uses wood material `*5n_49n(wpc/zm_tm_dirt01:wpc/zm_tm_wood_planks03)`. Mesh 90 is another two-triangle plane at X=15.239999771118164. The commit's `game.json` maps that material to `wood`.
- **Trigger:** Fire a penetration-capable hitscan weapon through one of those wood collision planes toward an actor on the other side.
- **Reference behavior and impact:** The map loader creates a separate triangle-mesh collider for each patch. After finding its front intersection, this routine moves 0.002 metres forward and asks the same collider for another forward intersection, assuming that intersection is a solid's exit. An open plane has no rear boundary in the same collider: once the ray starts beyond it, `cast_ray(..., false)` returns no hit and the routine immediately returns without damaging the actor. The chosen wood resistance and remaining energy never matter. The same algorithm can also mistake a disconnected triangle in a larger patch for the exit, and excluding the entire collider through `crossed` then ignores any later surfaces belonging to that collider. The implementation therefore does not provide reliable material penetration on the actual prepared collision representation.
- **Future correction:** Derive entry/exit thickness from the original solid brush or another representation with verified volume semantics, or implement a documented thin-surface policy for open patches. Do not treat an arbitrary later triangle as a solid exit or permanently exclude a collider that can contain multiple separate crossings. Preserve actor deduplication independently of surface traversal.

## Evidence limits and retained behavior

- The recovered source supports the ordinary 5000-point first upgrade and 2000-point attachment price; those constants are not findings. Transaction acceptance still performs the inventory deposit before accepting the point deduction, so no claim of a partial failed purchase is made here.
- One closest hit region is selected per actor before the ray traversal, and the per-ray actor set prevents duplicate actor entries. No repeated-hit defect was identified in that particular mechanism.
- Exact original material penetration depth tables, resistance values, per-body energy costs, and maximum penetration counts were not established from the inspected weapon/GSC/attachment dumps. The draft's 0.08 body debit, eight-actor limit, four-collider limit, and material coefficients remain uncalibrated approximations; this report does not invent native replacement numbers or claim those specific numbers are proven wrong.
- This review establishes static discrepancies and integration defects. It does not establish compilation, runtime behavior, performance, or release readiness.
