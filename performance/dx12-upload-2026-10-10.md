# DX12 upload investigation, 2026-10-10

The preceding counted draw correction is commit `d8492963944bc733f2d70d2b6f29cecf0763f24a`. Its pinned dev-dynamic executable measured 7.155 FPS versus 31.662 FPS Vulkan at physical 2880x1620 in the matched combat workload. This investigation follows that correctness commit.

## Non-elevated diagnostic procedure

Nsight Systems 2026.3.2 successfully traced the existing pinned executable on Windows without elevation. Set `WGPU_BACKEND=dx12`, run from the pinned binary directory, and use:

```powershell
& '<nsight-install>/target-windows-x64/nsys.exe' profile `
  --trace=dx12 --sample=none --cpuctxsw=none `
  --dx12-gpu-workload=batch --dx12-wait-calls=true `
  --delay=65 --duration=20 --kill=false `
  --output='<external-output>/dx12' `
  '<pinned-bin>/origins.exe' --release-benchmark-combat '<external-output>/workload'
```

CPU sampling and context-switch tracing require administrator privileges on this installation; both were disabled. WDDM/system-wide tracing was not enabled. Application-level DX12 API interception and GPU submission timing worked. `--kill=false` leaves the application running after capture; this benchmark exits normally on completion. Check the shared game/capture slot before launch. Captures are diagnostic evidence and their frame rate is not acceptance timing.

Export for analysis with `nsys export --type=sqlite --output=<output.sqlite> <capture.nsys-rep>`. In `DX12_API`, join `nameId` or `objectNameId` to `StringIds.id`. Filter `start >= 0`: negative timestamps include resource state reconstructed from before capture and must not be counted as work inside the measured interval.

The 20-second capture (`dx12-diagnosis-20261010`) contained 73 Presents and 372,206 staging-resource SetName calls, approximately 5,099 staging creations per presented frame. Total CreatePlacedResource calls inside the capture were 381,343. This exposed thousands of individually allocated temporary resources for queued uploads. Batch GPU work lasted an aggregate 6.043 seconds across 219 submissions; instrumentation overhead means this is not an unprofiled GPU frame-time result. No CPU stack sampling was collected.

## Implementation

Pack DX12 Queue::write_buffer data into independent aligned ranges in a staging buffer of at least 1 MiB, allocating a larger buffer for an oversized write. Preserve copy order, target-range validation and initialization tracking. Flush/unmap before submission, retain the buffer through the existing submission lifetime tracking, and discard it only when that lifetime ends. Only the first copy transitions a fresh source buffer; subsequent copies retain COPY_SRC state. Invalid writes do not advance the used range. The staging buffer is not reused across submissions.

The existing development-only GPU integration probe adds chunk-boundary and repeated-destination-write cases. The Vulkan upload path is unchanged.

Both recorded backends used continuous Winit updates while focused and unfocused, with vsync off. This rules out configured background throttling, not every possible event-loop pacing problem. No Winit change is included in this candidate.
